# Mirroring

> If transparency depends on one website staying online, it isn't really transparent.

The most important architectural principle of Rishwat.fyi is that **the platform must not depend on one website** (plan §11). Everything that makes the data meaningful — schemas, APIs, dataset snapshots, exports, documentation, source code — is public and mirrorable, so the project can survive any single point of failure:

> Website A disappears → Mirror B continues → Dataset C survives → Fork D continues development.

This document explains how to run an independent mirror.

## What is mirrorable

The project publishes, without authentication:

- **Dataset snapshots** — CSV and JSON exports of all published reports (`GET /datasets/reports.csv` and `GET /datasets/reports.json`, or files under `data/exports/` generated by the export script)
- **A dataset manifest** — machine-readable metadata (`generated_at`, `counts`, `schema_version`) published alongside every export
- **The public API** — documented in [`docs/api.md`](api.md) and machine-readable at `/doc/openapi.json`
- **The schemas** — `data/schemas/report.schema.json` and the data dictionary
- **The source code** — the full repository, including the methodology, moderation rules, and seed data
- **This documentation** — every `docs/` file

Nothing a mirror needs is behind a login. The dataset endpoints are served with `Cache-Control: no-store` so mirrors can always fetch fresh copies.

## How to mirror

### Option A — mirror the live exports (simplest)

The dataset is available over plain HTTPS with no auth. Fetch the current snapshot and re-serve it as static files:

```bash
curl -o reports.csv https://api.rishwat.fyi/datasets/reports.csv
curl -o reports.json https://api.rishwat.fyi/datasets/reports.json
```

Host the files on any static host (GitHub Pages, Netlify, Cloudflare Pages/R2, an S3-compatible bucket, or a plain nginx/Apache directory). To keep a mirror current, schedule a periodic fetch:

```bash
# crontab — fetch fresh snapshots hourly
0 * * * *  curl -fsS https://api.rishwat.fyi/datasets/reports.csv -o /var/www/mirror/reports.csv
0 * * * *  curl -fsS https://api.rishwat.fyi/datasets/reports.json -o /var/www/mirror/reports.json
```

Keep the exported files under the exact names from `/datasets`, and preserve the manifest so readers can see when the snapshot was generated.

### Option B — generate your own exports from source

A mirror can produce the dataset independently from the code, so it does not depend on the live API at all:

```bash
git clone <repository-url>
cd rishwat-fyi
npm install
cp .env.example .env          # set DATABASE_URL, TEST_DATABASE_URL, JWT_SECRET
bash scripts/db-up.sh
npm run db:migrate
npm run db:seed
npm run export -w apps/api    # writes data/exports/reports-<YYYY-MM-DD>.csv/.json + manifest.json
```

The export script runs the same `exportRows` query the API uses, applies the same redaction, and writes a manifest next to the files. Any fork can regenerate the dataset from its own database at any time.

### Option C — mirror the whole project

For maximum independence, mirror the repository itself (a plain `git clone`, or a fork on a code host) plus the exported datasets. That gives future contributors the code, the schemas, the seed data, and a current snapshot — everything needed to stand up a new instance.

## The mirror manifest

Every export is accompanied by a `manifest.json` describing what was produced. The manifest is the standard way for mirrors to tell readers when a snapshot was generated and what it contains. It is written by `apps/api/scripts/export-dataset.ts` next to the export files, and includes at minimum:

```json
{
  "generated_at": "2026-08-20T00:00:00.000Z",
  "counts": { "reports": 1243 },
  "schema_version": "1.0",
  "files": [
    "reports-2026-08-20.csv",
    "reports-2026-08-20.json"
  ]
}
```

| Field | Meaning |
| --- | --- |
| `generated_at` | ISO 8601 UTC timestamp of when the snapshot was produced |
| `counts` | Row counts per dataset (e.g. `reports`) |
| `schema_version` | Version of the export schema, so consumers can detect breaking changes |
| `files` | The export files included in this snapshot |

Mirrors should publish their manifest at a stable, predictable URL (e.g. `/manifest.json`) so automated consumers can discover the latest snapshot and its `generated_at`.

## Independence guarantees

What a mirror receives is exactly what the public API serves, and nothing more:

- **No PII by construction.** Exports are built from an explicit allowlist of columns. Raw IP hashes, device fingerprints, submission token hashes, and office identifiers are structurally excluded — they are not redacted, they are never selected. See the data dictionary (§4 "Fields that are NEVER exported") and [`docs/privacy.md`](privacy.md).
- **Only published reports.** Exports contain only reports in publishable statuses (`validated`, `corroborated`, `evidence_backed`, `officially_acknowledged`). `submitted`, `rejected`, and `withdrawn` reports never appear. See [`docs/data-dictionary.md`](data-dictionary.md) and [`docs/methodology.md`](methodology.md).
- **Descriptions are redacted.** The `redacted_description` column has Aadhaar, mobile numbers, emails, and card numbers replaced with `[REDACTED]` before export.
- **No authentication required.** Dataset endpoints and the OpenAPI spec are public, so a mirror never depends on credentials or on a specific operator's goodwill.
- **Reproducible.** Because the schema, methodology, redaction code, and export scripts are open source and version-controlled, a mirror can regenerate and verify the dataset independently — it does not have to trust the numbers on the live site.
- **Survival.** A mirror is a read-only copy and therefore cannot be censored, "quietly erased", or taken offline by pressure on the original operator. That is the point: the data is the infrastructure, and infrastructure must be replicable.

## Data quality note for mirrors

Please reproduce the notice from the methodology when serving mirrored data:

> Citizen reports represent reported experiences and are not automatically verified findings of wrongdoing.

And remember the limitations in [`docs/methodology.md`](methodology.md): aggregates reflect what was reported, not a census; below-threshold cells are `null` by design; and the dataset measures patterns and experiences, not guilt.
